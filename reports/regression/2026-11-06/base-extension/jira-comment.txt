h3. Findings
# *baseExtension eventID is fully supported (PASS).* Every allowed manufacturer event (commission, pack, SSCC-to-SSCC pack, ship, return ship, return receive, damaged, stolen, lost, expired, destruction, export) returned the same HTTP 202 and the same warnings with the wrapper as without it. The {{event_ids}} in each response matched the UUID inside baseExtension, so the platform reads the ID from there rather than minting its own.
# *Idempotency is shared across both placements (PASS).* Reusing a baseExtension eventID on a new payload was rejected with 409 DUPLICATE_EVENT_ID ("Event ID ... was already ingested"). The same ID sent as a top-level eventID was rejected too, so both placements write to the same uniqueness store, as the Technical Guides state.
# *Observation: the Recall Initiation sample cannot be sent by a manufacturer.* The docs sample uses bizStep {{holding}}, and the manufacturer key gets 403 PARTNER_TYPE_BIZSTEP_MISMATCH (allowed: commissioning, packing, shipping, receiving, destroying, inspecting, decommissioning). The guide also says a Destruction "should be preceded by a Recall Initiation", which a manufacturer cannot submit. Product should confirm which role owns recall initiation. Stock Adjustment ({{stock_taking}}) is likewise blocked for the manufacturer, which is expected if it belongs to facilities.
# *Noise, not defects:* the warnings UNKNOWN_SGLN, UNKNOWN_SGTIN, UNKNOWN_PARTY_GLN, PARENT_NOT_FOUND, UNCOMMISSIONED_CHILD, SHIPPING_WITHOUT_COMMISSIONING, NO_REGULATORY_APPROVAL, UNAUTHORIZED_INSPECTING_EVENT and INVALID_LOT come from the docs samples' placeholder GS1 data (prefix 0614141). They were identical in A and B.
