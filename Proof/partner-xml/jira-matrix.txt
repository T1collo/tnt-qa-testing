h3. Findings
*Overall verdict: FAIL.* *31/53 PASS, 22/53 FAIL.* The core checks work: XML validation, the size limit, session auth, duplicates and XXE protection. The failures fall into 7 defects (below), 4 of them High.

h4. Defects
# *[High] 10 of 53 uploads (19%) never finish.* They stay "accepted" or "processing" with no result, no diagnostics and no failure, more than 20 minutes after upload (normal jobs finish in about 1 minute). The partner is never told the outcome. Affected inputs: UTF-8 BOM (X06), UTF-16 (X08), EPCISBody without EventList (X12), SBDH without Sender/Receiver (X15), eventTime without Z (X25), commissioning with disposition in_transit (X28), 12-digit SGTIN (X32), shipping without bizTransactionList (X36), packing items never commissioned (X40), shipping a case never commissioned (X42). X06 and X08 are valid files, and X40 and X42 should complete with a warning. Example: request 3089925c-4ac7-4fe0-b83f-0805f6754f9f (X42).
# *[High] Events inside one document are not processed in document/eventTime order.* ObjectEvents (commission, ship) appear to be processed before AggregationEvents (pack). Every valid journey (commission > pack cases > pack pallet > ship) gets SHIPPING_WITHOUT_COMMISSIONING ("No prior aggregation (ADD) ... before shipping") plus INVALID_DISPOSITION ("in_transit" → "in_progress" for the pallet SSCC). The pallet can be left "in_progress" after it has shipped. Seen in X01, X04, X05, X07 and X52, and the same on the integration API.
# *[High] Integrity rules are raised as warnings only, so the bad event is stored.* The same item was packed into two cases: CHILD_ALREADY_AGGREGATED, 3/3 accepted (X41). A destroyed item was packed: SERIAL_ALREADY_DESTROYED ("terminal disposition destroyed — no further transitions allowed"), 3/3 accepted (X47).
# *[High] Product soft blocks never fire.* Unknown or not-owned GTINs should be accepted but flagged; here they are accepted with no flag at all. An unknown GTIN produced no UNKNOWN_SGTIN (X44). Another manufacturer's GTIN (Xarelto, Bayer) was commissioned by this partner with no warning (X45). Both are the same on the integration API, so nothing in the flags or reports would surface these products.
# *[Medium] The 50,000-EPC limit counts location GLNs as EPCs.* A document with exactly 50,000 serials is rejected: "Document appears to contain 50100 EPCs" (X50). The extra 100 are the readPoint/bizLocation of each event. The Async page over-counts the same way (1 item shows as "4 EPCs").
# *[Medium] An EPCIS 2.0 XML document (xsd:2, schemaVersion 2.0) is accepted and processed (X14)*, although the upload page says "EPCIS 1.2 XML only".
# *[Medium] Markup in lotNumber is stored.* An escaped <script> lot was accepted with only the INVALID_LOT warning that every unregistered lot gets (X62). Confirm it is escaped wherever lots are displayed.

h4. Gaps in the Async submissions page
* *Partial outcomes show as "succeeded"* (label "succeededpartial"): X21 1/2, X33 1/2, X46 1/2, X48 99/100. Dropped events are easy to miss.
* *No per-event diagnostics for single-event documents or failed jobs.* /diagnostics returns 404 "Diagnostics are not available for this submission" (X24, X44, X45, X62 and all 16 failed jobs). The partner sees a warning or error code but not which event or field caused it.
* *Stuck jobs never time out*, and clicking the row opens no detail (X42).
* The page header still says "Track outcomes for POST .../events/async"; it does not mention uploads.
* In diagnostics, each rejection reason is listed twice: once under its real code and once as a generic "WARNING" with the same message (X02a/X02b).

h4. Error codes that differ from the Technical Guides (rule enforced, so marked PASS)
* INVALID_XML_STRUCTURE instead of MISSING_EPCIS_BODY (X11), MISSING_EVENT_LIST (X13) and INVALID_ACTION (X27).
* MISSING_NEEDED_FIELDS instead of MISSING_REQUIRED_FIELD (X20, X26, X35), MISSING_ILMD (X29) and MIXED_LOT_IN_COMMISSIONING (X31).
* Oversize files return a plain 413 "Payload Too Large" with no PAYLOAD_TOO_LARGE / MESSAGE_SIZE_EXCEEDED code (X03, X53).
Either the API should return the documented codes or the guide should be updated, because partners map these codes.

h4. Reference SAP ATTP file (SC_EP_NT_O_BXCEKSE (1).XML). Platform correct; action for PM
* At 25.8 MB the full file is over the 10 MB limit and is rejected (413). The page also blocks it before sending.
* Slices under the limit are rejected event by event: "Foreign MAH commissioning requires sourceList". The product is imported (GS1 prefix 4008500), and the guide requires sourceList (foreign MAH GLN) and cbvmda:countryOfOrigin. The SAP export has neither.
* Partners exporting from SAP ATTP need guidance: split files to ≤10 MB and ≤50,000 EPCs, and add sourceList and countryOfOrigin for imported products.

h4. Working as expected
* Malformed XML, non-EPCIS XML, JSON saved as .xml, CSV (415 UPLOAD_FORMAT_PLANNED) and empty files are all rejected. The 10 MB limit is enforced in the page and on the server.
* XXE (file:///etc/passwd) and entity expansion are refused (INVALID_XML_STRUCTURE). No file content was leaked.
* eventIDs are preserved, both top-level and inside baseExtension (X01, X04). A re-upload is rejected with DUPLICATE_EVENT_ID (X22).
* FUTURE_EVENT_TIME, STALE_EVENT_TIME (warning), INVALID_EXPIRY_FORMAT, DUPLICATE_EPC_IN_EVENT, PARTNER_TYPE_BIZSTEP_MISMATCH and partial acceptance (99/100) all behave as documented. Upload without a session returns 401.
* The warnings UNKNOWN_SGLN, INVALID_LOT, UNKNOWN_PARTY_GLN and PARENT_NOT_FOUND come from the test master data and are not counted as defects.
